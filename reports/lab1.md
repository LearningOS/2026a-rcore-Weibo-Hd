## 一、实现的功能

本次实验在 ch3 框架上实现了 `sys_trace` 系统调用（编号 410）。

具体做法是：为每个任务在 TCB 中增加一张以 syscall id 为下标的调用计数表，在系统调用分发入口处「先计数、再处理」，这样查询 trace 自身调用次数时，本次调用也会被计入。`sys_trace` 支持三种请求：读取指定用户地址的一个字节、向指定用户地址写入一个字节、查询当前任务对某个系统调用的调用次数；请求编号非法时返回 -1。

由于本章尚未引入地址空间隔离，读写用户内存未做合法性校验，这部分留待 ch4 处理。

## 二、简答作业

### 2.1 用户态执行特权操作的行为

实验使用的 SBI 为 **RustSBI Prototyper v0.4.1（jump 模式）**，固件位于 `bootloader/rustsbi-qemu.bin`，对应上游 revision `1e10645e9a3cc6230988b037df506f97310555b7`，加载地址 `0x80000000`，内核入口 `0x80200000`。

三个越权测例的表现如下：

| 测例 | 越权行为 | 触发异常 | 内核输出 |
| --- | --- | --- | --- |
| `ch2b_bad_register` | 在 U 态执行 `csrr sstatus`，读取 S 态 CSR | IllegalInstruction | `[kernel] IllegalInstruction in application, kernel killed it.` |
| `ch2b_bad_instructions` | 在 U 态执行 `sret` 这条特权指令 | IllegalInstruction | 同上 |
| `ch2b_bad_address` | 向 `0x0` 写入一个字节 | StoreFault | `[kernel] PageFault in application, bad addr = 0x0, bad instruction = 0x...` |

结论：进入 U 态后，CSR 访问和特权指令都会被硬件拦截成非法指令异常；而对未授权物理地址的访问会被 PMP 拦下（RustSBI 设置的 PMP 区域中，低地址段为 `-wr`），表现为 StoreFault。这两种情况内核都会终止当前任务并调度下一个任务，程序无法继续执行。

测试方法：在 `os` 目录执行 `make run BASE=2`，逐个运行上述测例。

### 2.2 `trap.S` 中 `__alltraps` 与 `__restore` 的作用

**(1) 刚进入 `__restore` 时 `sp` 的含义，以及它的两种使用情景**

此时 `sp` 指向内核栈上为本次 trap 分配的 `TrapContext` 的起始地址，也就是那块 34×8 字节区域的低地址端。

两种使用情景：

- **trap 处理完毕返回**：`trap_handler` 返回后直接落入 `__restore`，此时 `sp` 就是刚才 `__alltraps` 压好的那个 `TrapContext`，恢复后 `sret` 回到被打断的用户指令继续执行。
- **任务切换后恢复**：`__switch` 切入另一个任务时，会把该任务 TCB 中保存的 `task_cx`（其 `ra` 指向 `__restore`、`sp` 指向该任务内核栈上的 `TrapContext`）恢复出来，于是从 `__restore` 开始执行，进入的是那个任务的用户态。

**(2) L43–L48 特殊处理的三个寄存器及其意义**

```riscv
ld t0, 32*8(sp)   # sstatus
ld t1, 33*8(sp)   # sepc
ld t2, 2*8(sp)    # 用户 sp（存在 TrapContext 的 x2 槽位）
csrw sstatus, t0
csrw sepc, t1
csrw sscratch, t2
```

- `sstatus`：决定 `sret` 的行为。其中 SPP 位决定返回后的特权级（0 表示 U 态），SPIE 位决定返回后是否重新开中断。不恢复它就无法正确回到用户态。
- `sepc`：返回地址，`sret` 会把 PC 置为它的值，即用户程序被打断的那条指令。
- `sscratch`：存放用户栈指针。恢复它是为了让下一次 trap 时 `__alltraps` 开头的 `csrrw sp, sscratch, sp` 仍能正确完成内核栈与用户栈的交换。

**(3) L50–L56 为何跳过 `x2` 和 `x4`**

- `x2` 是 `sp`。此时 `sp` 正被用作 `TrapContext` 的基址，不能在循环里被覆盖；用户栈指针另外保存在 `sscratch` 和第 2 个槽位中，最后由 `csrrw sp, sscratch, sp` 一次性换回。
- `x4` 是 `tp`（线程指针）。用户程序（Rust 用户库）并不使用它，内核侧还可能用它指向与 hart 相关的数据，因此没有必要保存和恢复。

**(4) L60 `csrrw sp, sscratch, sp` 执行后两个寄存器的意义**

- `sp`：用户栈指针，此时已回到用户栈。
- `sscratch`：内核栈顶指针（`TrapContext` 已通过 `addi sp, sp, 34*8` 释放），供下一次陷入时交换使用。

**(5) `__restore` 中的状态切换指令，以及为什么执行后会进入用户态**

状态切换发生在最后的 **`sret`** 指令。

`sret` 会做三件事：按 `sstatus.SPP` 决定返回的特权级（SPP = 0 → U 态）、把 `sepc` 装入 PC、把 `sstatus.SPIE` 复制回 `sstatus.SIE`。由于前面已经把 SPP 恢复成陷入前的值（用户态为 0），所以 `sret` 执行后 CPU 从 S 态回到 U 态，并从用户程序被打断处继续执行。

**(6) L13 `csrrw sp, sscratch, sp` 执行后两个寄存器的意义**

这是 `__alltraps` 开头的那条交换指令（`__alltraps` 位于文件前部，行号即此处的 L13）：

- `sp`：内核栈指针，指向当前任务内核栈的栈顶，随后在此之上分配 `TrapContext`。
- `sscratch`：用户栈指针，被暂时寄存，稍后写入 `TrapContext` 的 x2 槽位。

**(7) 从 U 态进入 S 态由哪条指令触发**

由用户程序执行的 **`ecall`** 指令触发。它产生 `Environment call from U-mode` 异常，CPU 转而跳到 `stvec` 指向的 `__alltraps`，从而进入 S 态的内核代码。

## 四、对实验设计的一些看法（可选）

本次实验的难点不在代码量，而在「本次调用也计入统计」这个细节：如果把计数放在分发之后，`count_syscall` 查到的值会永远比预期少 1。把计数放在 `syscall()` 入口处，逻辑上最自然，也顺带覆盖了未来新增的系统调用。

另外，本章尚未引入地址空间，`sys_trace` 直接解引用用户传入的裸指针，这在 ch4 会成为必须修复的安全问题，两个章节之间的衔接设计得很自然。
