## 一、实现的功能

实现了 `enable_deadlock_detect`(469) 和银行家算法的安全检查。把进程内的信号量、互斥量各自当成一类资源：信号量用 `count` 作 Available、按 tid 记录每个线程持有的份数；互斥量容量为 1，只记持有者和等待者。`mutex_lock` / `semaphore_down` 在将要阻塞时把本次申请计入 Need，构造三张表判断有没有安全序列，没有就返回 `-0xDEAD`。另外补齐了 `sys_get_time`。本次实验用时约 3 小时。

## 二、简答作业

### 2.1 需要回收的资源

主线程退出等于整个进程退出，这条路径上要还的东西分几层：

**线程私有的用户资源（`TaskUserRes`）**：tid、trap context 所在的物理页、用户栈占的页。tid 必须还给 `RecycleAllocator`，否则新建线程会一直往后分配，栈和 trap_cx 的地址也跟着涨。这几个资源的释放需要回写 PCB 里的分配器，所以代码里没有边遍历边释放，而是先把各线程的 `res` 取出来放进 `recycle_res`，等 `drop(process_inner)` 之后再统一析构，避免拿着 PCB 的借用又去借它一次。

**内核栈**：不能立刻回收。正在退出的这个线程还在自己的内核栈上跑 `exit_current_and_run_next`，栈一还就当场崩了。所以 0 号线程被 `add_stopping_task` 挂进一个待回收队列，等 `waittid` 或者父进程收尸时再释放；其它线程只是把 Arc 丢掉，最后一个引用消失时 TCB 析构，内核栈随之归还。

**地址空间**：`memory_set.recycle_data_pages()` 把用户页和各级页表页还给帧分配器。这一步必须在各线程的 trap_cx / ustack 回收之后，因为那些页也在同一套页表里，顺序反了就会把同一批物理页释放两次。

**其它**：文件描述符表（关文件、摘管道端）、子进程（转给 initproc 领养）、以及 PCB 自身——从 `pid2process` 摘除、标记 zombie、`tasks.clear()`，最后靠 Arc 归零释放。

### 2.2 其它线程的 TCB 的引用位置

| 位置 | 是否需要专门回收 | 原因 |
| --- | --- | --- |
| 调度器就绪队列 | **需要**，`remove_inactive_task` | 否则调度器会把一个 `res` 已经被取走的线程再次选中，下次进内核 `res.as_ref().unwrap()` 直接 panic |
| 定时器队列 | **需要**，同上 | sleep 中的线程挂在上面，到期后 `wakeup_task` 会把已退出的线程塞回就绪队列 |
| 当前 Processor 的 `CURRENT_TASK` | 不需要 | 只可能是正在退出的这个线程，`take_current_task` 已经把它摘走了 |
| 互斥量 / 信号量 / 条件变量的等待队列 | 不需要 | 这些原语是进程私有的，随 PCB 一起释放；被阻塞的线程不在就绪队列里，也不会被调度到 |
| 进程的 `tasks` 数组 | 需要，最后 `tasks.clear()` | 这是进程自己对所有线程的索引 |
| 待回收队列（0 号线程） | 由 `waittid` 负责 | 因为内核栈还在用，只能延迟释放 |

判断标准其实就一条：**这个引用会不会让线程再被调度起来**。会的必须摘（就绪队列、定时器队列），不会的（阻塞在同步原语上的）可以留给 PCB 一起释放。

### 2.3 Mutex1 与 Mutex2 的区别

两者的 `lock` 前半段一样，区别在 `unlock` 的语义。

Mutex1 是"解锁再竞争"：`unlock` 先把 `locked` 置 false，然后把队首唤醒；被唤醒的线程回到 `loop` 顶部重新检查 `locked`，抢不到就再排一次队。

Mutex2 是"直接移交"：`unlock` 时如果队列非空，**保持 `locked = true`**，只把队首唤醒，锁的所有权直接给它；只有队列为空才置 false。

由此带来的问题：

**插队与饥饿。** Mutex1 在"置 false"和"被唤醒者真正运行"之间有一个窗口，新来的线程可以直接 `lock` 成功，被唤醒的线程白醒一次又回去排队。竞争激烈时等待者可能反复被插队，表现为饥饿甚至活锁。Mutex2 的队首一定能拿到锁，是 FIFO 的。

**唤醒的有效性。** Mutex1 每次 `unlock` 唤醒一个，但被唤醒者可能重新入队，于是需要下一次 `unlock` 再唤醒它。如果这期间锁被新线程长期持有，等待者就一直睡着。Mutex2 唤醒一次就一定成功。

**Mutex2 的隐含前提。** 它假设被唤醒的线程一定会继续跑下去并把锁当成自己的。如果这个线程在真正运行前被 kill 掉，或者在进程退出时被清理，锁就永远停在 `locked = true` 且没有实际持有者，其它线程全部睡死。Mutex1 没有这个风险——它在 `unlock` 时已经把 `locked` 清掉了，最坏情况只是白醒一次。框架里靠 `remove_inactive_task` 把这类线程从就绪队列摘掉来兜底，但这是个隐含约定，不是 `Mutex` 接口本身保证的。

**开销。** Mutex1 的等待者每被唤醒一次都要重新进临界区判断，可能多出几次上下文切换；Mutex2 一次切换就完成交接。

本实验的实现取的是 Mutex2 的思路：`unlock` 时若有等待者就不清 `locked`，只唤醒队首；被唤醒的线程在 `lock` 返回前把 owner 改成自己，这样死锁检测看到的持有者是对的。

## 四、其他

### 4.1 资源怎么建模

银行家算法要三张表，关键在于"一类资源"怎么划。我的做法是把进程内**每个信号量**和**每个互斥量**都当成独立的一类资源：

- 信号量的 `count` 就是 Available（可能是负数，表示有人在等，取 0 处理）；
- 互斥量容量固定为 1，占用时 Available 为 0、空闲时为 1。

这样"线程 A 持锁 1 等锁 2、线程 B 持锁 2 等锁 1"这种环也能判出来，而不是只能发现自死锁。

代价是需要额外记账：原来 `Semaphore` 只有 `count` 和等待队列，看不出**哪个线程**拿了多少份，而 Allocation 是按线程的。所以给 `SemaphoreInner` 加了一个按 tid 下标的 `alloc` 数组，在 `down` 返回时加一、`up` 时减一；互斥量则记一个 owner。Need 不用额外存，各原语的等待队列里就有。

### 4.2 检测时机选在"将要阻塞"

最初的写法是每次 `mutex_lock` / `semaphore_down` 都跑一遍安全性检查，结果很容易误伤：资源明明还有余量、这次申请立刻就能满足，却因为别的线程构成了一个不安全状态而被拒。

后来改成只在**真的会阻塞**时才检查（互斥量已被占用、信号量 `count <= 0`），能立刻拿到的申请直接放行。这样既不会漏掉真正的死锁——不死锁的前提就是不阻塞——也不会把正常路径判死。

这一点在 `ch8_deadlock_sem1` 里体现得很直接：三个线程先后申请资源，前两个申请在当时的状态下都能构造出安全序列，第三个才会被判为不安全。所以这个测例断言的是"至少有一个子线程返回值不为 0"，而不是"第一个就被拒"。银行家算法是安全性检查，本来就不保证第一时间发现环。
